# hermes-voice-sidecar

Отдельный процесс для голосового ввода: сам открывает микрофон и сам
распознаёт речь — локально, без сети и без запущенного Hermes API server.

Ядро распознавания — **GigaAM v3 e2e CTC** (Sber, лицензия MIT и на код, и на
веса) в экспорте ONNX int8, ~215 МБ. Модель русскоязычная и только
русскоязычная: аргумент `--language` остался ради совместимости со старым
вызовом и ни на что не влияет. Признаки — лог-мел-фильтрбанк на 64 полосы,
посчитанный точно по Kaldi (`src/fbank.rs`), инференс — onnxruntime
(`src/asr.rs`), декодирование — жадный CTC.

Собранный бинарь лежит в `resources/bin/win/voice-sidecar.exe`, рядом с ним —
`onnxruntime.dll` (сборка 1.23.0 для win-x64, ~14 МБ). Оба файла попадают в
сборку через `extraResources` (см. `electron-builder.yml`), как `companion.exe`
и `tool-connector.exe`. Библиотека подгружается динамически, по имени, из
каталога самого exe — крейт `ort` собран с фичей `load-dynamic`, так что
несовпадение ABI между mingw-сборкой сайдкара и MSVC-сборкой onnxruntime роли
не играет: наружу торчит только C ABI.

Подписывать нужно оба файла: `signExts` в `electron-builder.yml` включает
`.dll`, так что electron-builder делает это сам, если задан сертификат.

Со стороны Electron им управляет `src/main/voice-sidecar.ts`.

## Режимы

| Запуск | Что делает |
| --- | --- |
| `voice-sidecar.exe` | читает WAV (16 кГц, моно, PCM) со stdin, печатает `{"text": "..."}` |
| `voice-sidecar.exe --record` | сам пишет с микрофона; команды на stdin: `partial` — промежуточный текст, `stop` — финальный |
| `voice-sidecar.exe --serve` | резидентный режим: живёт между диктовками, команды на stdin — `start`/`partial`/`stop`/`cancel`/`quit` |
| `voice-sidecar.exe --warm` | только скачивает и кэширует модель, ничего не распознаёт |
| `voice-sidecar.exe --probe-audio` | диагностика: перебирает способы открыть микрофон и печатает результат каждого |
| `--language ru` | язык распознавания (по умолчанию `ru`) |

Весь вывод — по одному JSON-объекту на строку: `{"status": ...}`,
`{"partial": ...}`, `{"text": ...}` или `{"error": ...}`. Ошибки тоже приходят
как JSON, чтобы вызывающей стороне не приходилось разбирать stderr.

Кэш модели — в каталоге из переменной `HERMES_VOICE_MODEL_DIR`
(Electron указывает на `%LOCALAPPDATA%\HermesVoice`); без неё берётся временный
каталог системы. Качается один раз, докачка безопасна: файл сначала пишется
как `*.part` и переименовывается только целиком.

Резидентный процесс **не держит модель в памяти**. 215 МБ весов висели бы в
RAM всё время работы приложения ради нескольких секунд диктовки в день, так
что сессия onnxruntime поднимается на команду `start` — в фоне, параллельно
записи — и освобождается сразу после `stop`/`cancel`. К моменту, когда человек
договорил, она обычно уже готова, поэтому на задержке это не сказывается.

## Контракт модели и признаки

Граф принимает **уже посчитанные** признаки, а не звук:

| Тензор | Тип | Форма |
| --- | --- | --- |
| `features` | f32 | `[batch, 64, seq_len]` |
| `feature_lengths` | i64 | `[batch]` |
| `log_probs` (выход) | f32 | `[batch, seq_len/4, 257]` |

Имена именно такие. У исходного чекпойнта NeMo они назывались
`audio_signal`/`length`, и у RNN-T-экспортов GigaAM так и осталось — но у
этого экспорта нет, и попытка обратиться по старым именам падает с
`Invalid input name`.

Препроцессинг (`src/fbank.rs`) у GigaAM v3 свой и отличается от Kaldi и от
whisper в каждой детали: окно 320 отсчётов (20 мс), шаг 160, длина БПФ тоже
320 (то есть 161 бин), края НЕ дополняются, спектр по мощности, логарифм
натуральный от значения, зажатого снизу в `1e-9`, нормализации нет. Окно и
матрицу мел-фильтров мы не считаем по формуле, а держим готовой таблицей
`src/gigaam_v3_fbank.bin` (42 КБ), снятой из `onnx-asr` — той реализации,
которой делался этот экспорт.

Сверено с эталоном на реальной записи: число кадров совпадает, расхождение
признаков не больше `4e-4` по модулю (округление f32 в БПФ), распознанный
текст совпадает посимвольно. На 26 секундах речи инференс занимает около
секунды на одном ядре.

## Сборка под Windows

Бинарь только для Windows. Кросс-сборка с Linux, без wine:

```bash
rustup target add x86_64-pc-windows-gnullvm
# llvm-mingw: https://github.com/mstorsjo/llvm-mingw/releases — распаковать и
# добавить его bin/ в PATH (нужны x86_64-w64-mingw32-clang и -ar)
cargo build --release --target x86_64-pc-windows-gnullvm
x86_64-w64-mingw32-strip target/x86_64-pc-windows-gnullvm/release/voice-sidecar.exe
cp target/x86_64-pc-windows-gnullvm/release/voice-sidecar.exe ../../resources/bin/win/
```

**Статическая линковка обязательна** — она задана в `.cargo/config.toml`
(`-C target-feature=+crt-static -C link-args=-static`). Без неё бинарь
импортирует `libunwind.dll` из состава llvm-mingw, которой на обычной машине
нет, и процесс завершается при загрузке молча, без единой строки вывода.
Проверить, что зависимостей от толчейна не осталось:

```bash
x86_64-w64-mingw32-objdump -p voice-sidecar.exe | grep 'DLL Name'
```

В списке должны быть только системные библиотеки Windows (`kernel32`,
`ole32`, `advapi32`, `api-ms-win-crt-*` и подобные) — ничего вроде
`libunwind.dll`, `libc++.dll` или `libwinpthread-1.dll`.

Нативная сборка под Linux (`cargo build` без `--target`) не проходит: у
`native-tls` на Linux бэкенд OpenSSL, которого в окружении может не быть. Для
Windows это неважно — там используется schannel. А вот `cargo test` под Linux
работает и его стоит гонять: юниты на фильтрбанк, CTC-декодер и разбор словаря
от платформы не зависят.

`onnxruntime.dll` берётся из официального релиза, отдельно от cargo:

```bash
curl -sSL -o ort.zip \
  https://github.com/microsoft/onnxruntime/releases/download/v1.23.0/onnxruntime-win-x64-1.23.0.zip
unzip -j ort.zip 'onnxruntime-win-x64-1.23.0/lib/onnxruntime.dll' \
  -d ../../resources/bin/win/
```

## Захват звука и почему он такой странный

`--record` открывает микрофон напрямую через WASAPI (`src/wasapi.rs`), а если
не выходит — через устаревший WinMM/`waveIn` (`src/winmm.rs`). Перебирается
длинный список вариантов: обе модели COM-апартамента, разные категории потока,
raw-режим, размеры буфера, `IAudioClient3`, монопольный режим, формат драйвера
и явный PCM с конвертером движка. Это не перестраховка — на машинах с
микрофонными массивами Intel Smart Sound часть этих комбинаций отваливается, и
список написан по результатам реальной диагностики.

`--probe-audio` прогоняет тот же список и печатает, что ответил драйвер на
каждую попытку, с кодом ошибки. Это первое, что стоит запустить, когда
голосовой ввод не работает у пользователя.

## Если микрофон не открывается ни одним способом

Если `--probe-audio` показывает отказ **по всем** вариантам, причём и WASAPI, и
`waveIn` отвечают «неверный параметр» (`0x80070057` и `MMSYSERR 11`), — дело
почти наверняка не в коде и не в драйвере, а во внешней блокировке.

Kaspersky Endpoint Security не даёт неподписанным и незнакомым ему программам
доступ к устройствам записи звука (компонент «Предотвращение вторжений»), и
выглядит это именно так: обобщённая ошибка на любом API. Проверяется за минуту
— в отчётах Касперского, раздел «Предотвращение вторжений», появляются записи
«Приложению запрещено получить звук с вашей камеры или микрофона».

Лечится только со стороны политики безопасности: приложению выдаётся право на
доступ к устройствам записи звука, желательно с привязкой правила к сертификату
издателя, а не к пути или контрольной сумме файла — иначе правило слетает при
каждом обновлении. Поэтому релизные сборки нужно подписывать; см. комментарий
о подписи в `electron-builder.yml`.
